# Appause Pro 支付与发码方案（设计稿）

> 状态：方案讨论稿，未实现。技术底座（Plan B）已就绪，缺的是"用户怎么付钱、码从哪来"这一层。
> 最后更新：2026-08-01

---

## 1. 现状（已完成的技术底座）

- **设备绑定的许可证令牌**：Cloudflare Worker（`worker/`）负责签发 **RS256 JWT**，私钥仅在 Worker 的 secret（`APPAUSE_PRIVATE_KEY`）里，永不进仓库。
- **本地验签**：App 内嵌**验证公钥**（`ServerKeys.kt`），对令牌做离线签名校验，不依赖服务器在线也能验证。
- **兑换流程**：App 内输入短激活码 → `redeemCode` POST 到 Worker `/api/redeem` → Worker 校验码有效且设备未超限 → 返回 JWT → App 本地验签存下。这条链路已经能跑通（本地用 `/admin/gencode` 生成的测试码已验签成功）。
- **导入令牌**：App 内 `importLicense` 可直接粘贴一段 JWT 文本本地验签，用于换设备 / 重装后恢复 Pro（已实现）。

也就是说，"付完钱拿到码 → 激活 Pro" 的后半段已经具备，本方案只补前半段（收款 + 发码）。

---

## 2. 支付模式决策

**采用一次性买断，不接订阅，不嵌入应用内购 SDK。**

理由：

- **隐私优先 + MIT 开源**：Google Play Billing / 微信支付 / 支付宝 SDK 都要嵌第三方、且存在政策与抽成约束。Appause 主打无遥测、开源，自助发码最干净。
- **平台抽成**：Play / 各支付渠道抽 15%–30%。自助发码几乎零成本，收入全留。
- **Play 上架风险**：无障碍类"专注 / 防沉迷"App 在 Play 有过拒审先例，且 Play 对这类功能有限制。买断 + 自助发码不依赖商店支付，分发走 GitHub Releases + 蓝奏云镜像即可。
- **买断比订阅更友好**：这类工具用户一次付费、长期用，订阅反而劝退。

---

## 3. 发码与交付流程（推荐）

1. 落地页 / GitHub README 放一个**购码入口**（文字链接或按钮）。
2. 用户付款后，拿到一个**一次性激活码**（形如 `APP-XXXX-XXXX`）。
3. 在 App 的 Pro 页点「用激活码激活」→ 走已有的 `redeemCode` → Worker 校验 → 发令牌 → 本地解锁。
4. 收款与发码解耦：收款可用极轻量方式（见第 5 节），发码由 Worker 统一负责，App 端代码不用改。

---

## 4. 设备绑定与上限

- 每个激活码默认绑定 **2–3 台设备**（在 Worker 侧记 `deviceId` 列表，超上限返回 `device_limit_reached`，App 已有对应错误提示）。
- **换手机流程**：旧设备用 App 内「导出许可证」拿到 JWT；新设备装完后用「导入许可证（换设备 / 恢复）」直接灌入，不消耗新的绑定名额。
- 后续可做**自助解绑**：App 内加「解绑此设备」→ 调 Worker 把该设备令牌作废 → 释放一个名额，方便换机。

---

## 5. 收款渠道（按轻量到完整排序）

- **微信赞赏 + 半自动发码**（最快上线）：落地页放赞赏码，用户赞赏后截图/留言，你手动或脚本发码到邮箱。零开发成本，适合前期验证付费意愿。
- **轻量支付对接**：接一个不抽成太狠的渠道（如虎皮椒 / 易支付类原生支付页），付款成功回调里自动调 Worker 生成一个码并发到用户邮箱。
- **落地页购码二维码**：生成"购码二维码"贴到 README / 社交平台，扫码跳支付页，回调自动发码。

---

## 6. 以后可增强（不急，按需）

- **二维码购码**：落地页一键生成支付二维码，扫码即买即发。
- **自助解绑 / 设备管理**：用户在网页或 App 里查看已绑设备、远程解绑旧机。
- **优惠与分销**：早期支持者折扣码、推荐返利（仅在前端做，不影响 Worker 验签逻辑）。

---

## 7. 红线与安全

- **发布前务必确认 `ServerKeys` 用的是生产公钥**（已通过 commit `50203ae` 于 2026-07-29 换成生产密钥，本地也验签确认过）。绝不重用 dev 令牌，否则任何人都能解锁 Pro。
- 私钥只在 Worker secret，**绝不进仓库、绝不进客户端**。
- 严格遵守项目约束：**不引入账号系统、云同步、分析 SDK**。Worker 只签发与校验设备绑定令牌，不接收 / 存储 / 同步任何用户数据。
- 激活码本身是无状态校验（Worker 侧校验有效性 + 设备数），不要把用户邮箱等 PII 写进 JWT payload。
